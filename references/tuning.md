# 受控调优与瓶颈定位

## 优先级和实验记录

先满足客户功能质量门槛/基线质量不退化，再优化TTFT/TPOT。coding按已确认矩阵采用原生token命中率≥98%的热缓存条件，重点观察decode。性能目标取用户确认值；报告必须说明P95等何种统计量、冷热缓存、输出策略和成功率，不能自行把目标从尾延迟换成均值。

先在用户当前卡数内做比较，固定卡数约束未解除时不得扩容；未成功的扩容探索不抹掉已有配置结果。每个候选记录：唯一ID、父基线、唯一或明确的一组变化、假设、回退、质量/性能验收、停止条件。用于筛选的小格必须在计划里说明；最终验收仍覆盖确认的完整矩阵，不能以小格替代。

可比较的旋钮而非固定最佳值：

- MTP off/1/2/3及该镜像实际支持值；MTP是推理侧投机解码配置，不是重新训练。确认模型MTP权重、draft方法、接受率及运行初始化日志。flag存在不证明生效，3不一定胜过1。
- batch token预算、max-num-seqs、chunked prefill：更大预算可改善prefill但增加显存/调度压力和decode干扰，不能只按prefill吞吐选。
- APC与热副本覆盖、API server数、DP负载不均衡、调度队列。API worker数不等于GPU DP数。
- eager/图编译/decode-only capture：先核对镜像支持和实际图捕获；保留draft eager等模型安全限制。不能强行去除内核守卫，仅凭一个开关声称草稿图已启用。
- TP/DP/EP及P:D配比：保持总卡数准确，分别检查每组权重/KV占用、通信和负载。PD只有在connector兼容、KV传输正确之后才压测。

遇到较大变化先做2K工具链校验，再长输入最小格。变更期间不继续旧测试，不修改活动脚本及其导入依赖。失败实验也记入表，避免只留下最优一次。

## 资源归因

采集实际NPU Pod，不把构建/发压机器的CPU当NPU指标。每次重建后更新collector目标hostname/cohort。按5–10秒等合理周期自动记录每卡利用率、HBM占用、KV/running/waiting、CPU、内存、网络、HCCL及MTP原生计数；collector设时间、磁盘上限与STOP，保存时钟信息和采样开销。这是脚本采样频率，不是GPT查询频率；采集不需要模型持续在线。

观察区间要对齐request的prefill/decode时间段，不能拿整批平均利用率代表decode瓶颈。

| 观察 | 可支持的下一步 | 不能直接推出 |
|---|---|---|
| 某DP忙，其他DP空闲 | 检查路由/副本覆盖、队列、单长请求落点 | 模型本身没有并行能力 |
| 等待高且设备利用率低 | 检查admission、CPU/API、同步、KV组限制 | 卡不够，必须扩容 |
| HBM占用高 | 查KV/权重/碎片和余量 | HBM带宽已经饱和 |
| 网卡吞吐高 | 对齐通信阶段，必要时做独立HCCL/算子trace | 通信一定是关键路径瓶颈 |
| MTP接受率低/额外开销高 | 同工作负载比较更小MTP步数 | MTP3总是更快 |
| 客户端TTFT高，server queue/prefill不高 | 检查API层/事件上报、网络、其他未解释残差 | 自动把差值都归到通信或prefill |

使用版本支持的设备counter或独立短profiling验证带宽/算子瓶颈；profiling运行与正式时延分开，注明开销。没有计数器就写证据缺口，不为凑瓶颈结论杜撰百分比。

## 何时停

OOM、EngineDead、正式请求不完整、异常usage、错误后端、未排空、监控不足以覆盖下一格时停止发新负载并保留结果。近1M首次异常停止更高并发，先分清网关时限、引擎和输入/采集问题。不能把1次504直接当模型硬容量上限。

达到时间/卡数边界或连续候选无收益时，交付“已测配置中最佳”和未决限制，不说“全局最优”。确定性正确性测试不过的快配置不能晋升主基线。
